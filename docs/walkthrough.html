Wisen Walkthrough
Target architecture · steps 0–4 shipped · 5 in validation · 6–7 next

wisen

A harness that learns from how I work with coding agents. Every night it reads the day's agent sessions and finds where the work was hard. By morning it proposes a small change to the instructions my agents read. I approve it from my phone, it lands as a git branch, and two weeks later wisen measures whether the change helped.

observe→reflect→propose→approve→apply→measure↺
The problem

Agents produce transcripts nobody reads

I run Claude Code, Codex, Cursor, opencode, Gemini CLI and Pi every day. Each session leaves a transcript full of signal: the tool calls I rejected, the times I interrupted, the requests I rephrased three times. None of it changes how the agents behave tomorrow. wisen closes that loop without uploading my coding logs anywhere.

One night with wisen

The pipeline is modelled on sleep

The brain does not replay everything; it replays what mattered, then consolidates it. wisen has two model stages that work the same way. The Observer (NREM) reads a day's raw sessions and turns them into short, redacted notes called packets. The Synthesizer (REM) reads only packets and writes the morning reflection. That split is also where the laptop ends and the server begins.

Stage A → stage B

One boundary, two deployments

The server was built in two stages. In stage A every model call runs on the laptop and the server is only a mailbox: schedule, approval inbox, push notifications, with no model key at all. In stage B the REM half moves to the server so it can "dream" while the laptop sleeps. The privacy rule did not change between the two, because the packet boundary was there from the start: REM only ever needed packets.

Production-grade 1

The privacy line is code, not a promise

1 · At rest: local

Raw transcripts stay where the agents wrote them. wisen stores only derived data in ~/.wisen/wisen.db.

2 · Inference: excerpts

The laptop's model calls get capped excerpts: 400 characters per turn, up to 20 config files at 1,000 characters each.

3 · Cloud: packets only

If it is not a packet type, it does not cross. Both ends import the same schema module.

Every packet goes through the egress gate (the laptop's one exit check) in this order. A value that redaction would change inside a diff or an identifier rejects the whole packet; a human never approves a cut-short diff.

Selectallow-listed fields only
Redactkeys, tokens, home paths, emails
Truncatefree text and quotes to caps
Validatestrict model, extra fields forbidden
Recordlocal egress ledger (wisen egress)
Sendidempotent by content hash

How it is proven. Tests plant a marker string and a fake API key in fixture transcripts and assert that neither appears in any packet, that an off-schema packet is rejected, and that the same content always hashes to the same packet id. In stage B, a mock model that echoes its prompt checks that no marker reaches any server-side prompt or row.

Durability is an egress risk too. A durable job saves each step's output, so the Observer step saves its packet output, never raw turns, and any journal that held raw text is pruned when the job succeeds.

Experimental

The Gardener

The Gardener is the agent that turns reflections into proposed changes. It may edit only the instructions agents read: CLAUDE.md, AGENTS.md and skills, in each repo and in my home directory. Never repo code, settings or MCP config. The allow-list is a path check in the laptop's applier, so a proposal for any other path is refused even after approval. Files outside any repo, like ~/.claude/CLAUDE.md, are tracked by a wisen-managed git history (~/.wisen/gardener/home.git) whose working folder is my home directory, so every change is still a branch.

Before a proposal reaches me, wisen runs a replay: it re-runs past moments where I had to correct an agent, once with the current file and once with the proposed one, and checks whether the problem came back. It also replays a clean set, moments that went smoothly, which the change must not break. The proposal tool is declared requires_approval: the agent run pauses at that call and is stored until I decide.

Verification loop

How wisen knows it is climbing the hill

Each approved proposal is one step up the hill. A step counts only if it makes the work measurably better without making anything worse. Five metric layers, from "did work get done" down to "can we trust our own judge". Today the friction and cost metrics read Claude Code transcripts only; the other agents' transcripts lack the markers they rely on.

1OutcomeDid work get done?

Problems solved

solved = count(commits I authored that land on the default branch), each credited once, to the nearest session in that repo (a feature branch counts as one problem when it lands)

Read from each project's local git history. Squash-merged PRs are counted once a GitHub connector supplies merged-PR data.

wisen/evals/verification.py

Revert or re-fix rate (quality guard)

revert_rate = solved items reverted, or re-fixed within 7 days / solved

Stops "solved" from rewarding fast, wrong commits.

2CostWhat did it take?

Human-in-the-loop turns per PR

hitl_turns(PR) = Σ user turns across the sessions linked to that PR, from the first related session to the merge

My attention is the scarcest resource; this is the headline cost, shown next to tokens per problem.

Tokens and dollars per problem solved

tokens_per_solved = Σ tokens / solved dollars_per_solved = Σ costUSD / solved (where the transcript records it)
Claude Code transcripts · wisen/evals/miner.py
3FrictionHow hard was it?

Corrections per 100 user turns

corrections = tool_rejections + interruptions + explicit_corrections + rephrase_storms rate = corrections / user_turns × 100 (per day, per detector)

Deterministic code, no model: the "user doesn't want to proceed" marker, "[Request interrupted by user", a message starting with no / stop / wait / revert / wrong, and a rephrase storm (a second message within 60 seconds).

wisen/evals/miner.py

Friction half-life

half_life = mean(days_persisting) over frictions marked resolved

Days a friction survives before it stops recurring, from the nightly reflection's new / persisting / resolved labels.

wisen/evals/metrics.py
4Controlled checkDid the change cause it?

Replay pass rate, per config version

pass(case, config) = majority of 3 judge votes that the corrected behaviour did not recur when the case is replayed under config replay_rate(config) = Σ pass / cases clean_rate(config) = same, over the clean set

Shown on the proposal, for example "fixed 7 of 10 past cases, broke 0 of 20 clean ones", with the replay's model cost.

wisen/evals/replay.py · judge.py · runner.py
5TrustIs our own judge sane?

Alignment vs corrections

r = pearson(alignment_score(day), corrections_per_100(day))

The nightly reflection gives each day an LLM-judged alignment score; the code counts corrections independently. A healthy judge scores hard days low, so r should be clearly negative. Near zero means the score is noise. Reported by wisen eval.

Before: accept rule, shownEach proposal shows whether it meets the rule (replay rate up, clean rate not down): yes, no, or not enough cases to tell. I still decide.
After: field check2 weeks after merge, before vs after: helped if corrections per 100 turns fall more than 5% and tokens per problem rise no more than 5%; worse if corrections rise more than 5% or tokens rise more than 10%; otherwise no change.
RecordKept or revert proposed, with the reason. Rejection notes and results feed the next Gardener run.

Why both: daily field metrics are noisy because the work changes (a refactor day has more friction than a docs day). Replay holds the moments fixed and changes only the config, so it is the causal evidence; the field check confirms it held in real life.

Production-grade 2

Durability, end to end: the life of one Approve tap

Two machines, two doors, one meeting point. I use the app routes with my login; the laptop uses the device routes with its device token. They never call each other: the server's database is where they meet. Every step writes its fact before acting, every request carries an id so a retry is harmless, and the laptop pulls work with a cursor, so nothing is lost when either side crashes or sleeps.

Production-grade 3

Durable execution, built from scratch

The concept. A durable workflow is code that survives its own process dying. Each step's result is written down before the next step starts, so after a crash, a deploy or a laptop going to sleep, the work resumes from the last finished step instead of starting over. wisen needs this because model calls cost money and minutes, because a proposal legitimately waits hours for my decision and two weeks for its measure, and because the work is split across a laptop that sleeps and a server that does not.

recordMemoized steps

A job is a list of named steps. A finished step's output is saved; a rerun returns the saved output instead of calling the model again.

claimLeases

A worker claims a job with an expiring lease and heartbeats to keep it. A dead or sleeping worker's lease expires and the job goes back to the queue.

safetyReplay policy per step

Reads and model calls are safe to repeat. Side effects (create a branch, send a push) are not: an interrupted one fails the job for a human instead of running twice.

pauseWaits

A job parks until an event arrives, for example waiting for my decision on a proposal, or for the laptop's result.

laterTimers

A job with run_after in the future: the 7-day proposal expiry and the measure job 2 weeks after merge. Wake-ups may repeat, so handlers are idempotent.

dedupeRequest ids

Each request carries a unique id; the job row is its receipt. A resent request returns the existing job instead of starting a second one.

My approach. pydantic-ai runs each single agent call; everything between calls and between machines is a small engine I wrote on SQLite, the same code on the laptop and the server, each with its own database. One agent run is one step. On the server a job's runner column says who may claim it: the server runs its own jobs in-process, and device jobs are claimed by the laptop over HTTPS with the same lease rules.

ChoiceWhy
Hand-built engine on SQLiteTwo processes, one of which sleeps; one file per machine; no extra service on a 2 vCPU box. Building it is also the point of the project: learning orchestration from scratch.
DBOS as the fallbackIf the engine fails its crash tests or keeps costing more than the features on it, DBOS (in-process, SQLite) swaps in behind the same job interface. The proposal state machine stays hand-built either way.
Proven by crash testsKill the process between Observer and Synthesizer: the Observer is not called again and exactly one reflection is stored. A duplicate request id returns the existing job. An expired lease is requeued on startup.

Inside the job engine

The whole engine is three SQLite tables and a handful of functions (wisen/jobs.py, tables in wisen/store.py). It keeps nothing in memory that a restart would lose: every function commits its change before it returns.

stateDiagram-v2
  [*] --> queued: enqueue (runnable once run_after passes)
  queued --> leased: claim (lease 60 s, heartbeats extend it)
  leased --> succeeded: finish
  leased --> waiting: ctx.wait (parked until a signal or timeout)
  waiting --> queued: signal arrives / timeout passes
  leased --> queued: attempt failed, retry with backoff / lease expired
  leased --> failed: attempts used up / unsafe step interrupted
  failed --> queued: same request id rerun
  succeeded --> [*]
Job states. A failed attempt goes back to the queue after a backoff that starts at 30 seconds and doubles each attempt, capped at 1 hour.

Design rules the engine follows: only committed state exists; every job checkpoints after each phase; every step declares whether it is safe to rerun; request ids make retries harmless; timers are recomputed from stored jobs and wakes may repeat, so handlers are idempotent; crash-safe decisions are first-write-wins. These follow the lessons in Earendil's "Pi Durable" posts.

For the review

Production-grade and experimental, side by side

Production-grade

  • A privacy boundary enforced by one shared schema at both ends, proven by marker tests
  • Durable execution on SQLite: leases, memoized steps, replay policies, crash tests
  • A proposal state machine with compare-and-set moves and an audit log
  • Idempotent decisions across two approval channels; deterministic commits
  • A path allow-list enforced in the applier, not the prompt
  • A self-hosted server: systemd, Caddy, backups, device tokens

Experimental

  • Sleep as architecture: NREM on the laptop, REM on the server
  • An agent that edits its operator's agent instructions, behind a human gate
  • Correction moments mined from my own transcripts as an eval set
  • Counterfactual replay before every proposal
  • Measuring the judge: alignment score against counted corrections
  • Grep-first search: no vector index, so no second copy of the transcripts; search re-reads the originals at question time
